# ARC_036 — ZIP akış başlığı merkez diziniyle çelişiyor

> Karar: Bir ZIP girdisinin AKIŞ görünümü (yerel başlıktaki data-descriptor bayrağı + descriptor kaydı) merkez diziniyle çelişiyorsa arşiv, merkez dizinden okuyan araçlarda sorunsuz açılır ama akıştan okuyan araçlarda HİÇ açılmaz. Veri kaybı yoktur; kayıp birlikte çalışabilirliktedir ve yayıncı bunu başka hiçbir yerden öğrenemez.
> ⚠️ İhlal edilen belge GTFS değil **PKZIP APPNOTE 4.4.4**'tür. Bu yüzden kural `Spec` değil `Quality`, otoritesi `PROJECT_QUALITY`'dir.

## Tetikleme koşulu (kesin mantık)
Merkez dizindeki her girdi için yerel dosya başlığı (local file header, 30 bayt) okunur. Girdi ancak **üç koşul birlikte** sağlanınca tutarsız sayılır:

1. Genel amaçlı bayrakta **bit 3** (`0x0008`, data descriptor) set,
2. verinin ardında bir data descriptor bulunamıyor **ya da** bulunuyor ama içindeki `crc32`/`compressed_size`/`uncompressed_size` üçlüsü merkez dizinle tutmuyor.

Descriptor imzası (`PK\x07\x08`) APPNOTE'a göre **opsiyoneldir**; iki biçim de okunur. Verinin bittiği konum MERKEZ DİZİNDEKİ sıkıştırılmış boyutla hesaplanır — kurallara uygun akış zip'inde yerel alan sıfırdır ve oradan konum bulunamaz.

Bulgu **feed düzeyinde tektir**: etkilenen girdi sayısı `observed_value`da taşınır. Girdi başına bulgu basmak yayıncının tek hatasını girdi sayısı kadar tekrarlardı.

**zip64 girdileri atlanır.** 32-bit boyut alanları `0xFFFFFFFF` kaçışını taşır, gerçek değer extra field'dadır ve buradan okunamaz; okunamayan bir şeyi "çelişkili" saymak yanlış pozitif üretir.

## Yanlış pozitif / negatif (asıl tasarım riski)
- 🔴 **ASIL RİSK: data descriptor kullanımı normaldir, kusur DEĞİLDİR.** Kural yalnız bayrağa baksaydı korpusun büyük bölümünü suçlardı. **Ölçüldü (2026-09-08, katalogdan 200 feed'lik rastgele örneklem, 5 KB–5 MB):** feed'lerin **80'i (%40)** data descriptor'ı kurallara uygun kullanıyor — yerel boyutlar sıfır, descriptor yerinde ve merkez dizinle birebir. Gevşetilmiş bir koşul ~1.700 feed'e yanlış bulgu basardı.
- ✅ **Yayınlanan koşulla aynı 200 feed'lik örneklemde 0 bulgu.** Kural, kırılgan olduğu yerde (descriptor kullanan 80 feed) sınandı ve sessiz kaldı.
- **Yanlış negatif:** merkez dizini de bozuk olan arşivler bu kuralın konusu değildir — onlar zaten `ARC_001` (fatal, arşiv açılamadı) yolundan düşer. Bu kural yalnız "açılabilen ama akış görünümü çelişen" arşivi hedefler.
- **Kapsam sınırı:** karar merkez dizinden okunabilen alanlarla verilir; zip64 girdileri bilinçli olarak kapsam dışıdır.

## Kod değiştirirken minimum test matrisi
- Meşru akış zip'i (bayrak set, yerel boyutlar 0, descriptor doğru) → **bulgu YOK.** Bu satır kuralın FP kapısıdır; düşerse korpusun %40'ı yanlış bulgu alır.
- Descriptor imzasız yazılmış meşru akış zip'i → **bulgu YOK** (imza opsiyoneldir).
- zip64 kaçış değeri taşıyan girdi → **atlanır.**

| Senaryo | Beklenen |
|---|---|
| normal zip (bayrak yok) | `ARC_036` yok |
| bayrak set · boyutlar 0 · descriptor doğru | `ARC_036` YOK (meşru akış zip'i) |
| bayrak set · boyutlar dolu · descriptor yok | `ARC_036` (1 bulgu, `observed` = girdi sayısı) |
| bayrak set · descriptor var ama `usize` yanlış | `ARC_036` |
| bayrak set · boyut alanları `0xFFFFFFFF` (zip64) | `ARC_036` yok |
| merkez dizin de bozuk | `ARC_001` (fatal), `ARC_036` YOK |

## Teknik ek
### Dış araç eşleşmesi
- **MobilityData'da karşılığı YOK** (`NO_MD_EQUIVALENT`). Katalogda ZIP çerçeve tutarlılığını denetleyen bir kod bulunmuyor; MD bu arşivlerde bulgu üretmek yerine **çöküyor**: `GtfsInput.createFromPath()` arşivi commons-compress `ZipFile` ile açtıktan SONRA `hasSubfolderWithGtfsFile()` aynı dosyayı `java.util.zip.ZipInputStream` ile ikinci kez açar ve `ZipException` fırlatır; doğrulama hiç başlamaz.
- **2026-09-08'de MD 8.0.1 CLI ile yerelde ölçüldü:** `tdg-81618` → `ZipException: invalid entry size (expected 2271412232 but got 149 bytes)`, çıkış kodu 255, `report.json` içinde `"notices": []`. Aynı dosyaların içeriği normal çerçeveyle yeniden paketlenince MD **0,075 sn**'de doğruluyor (4 notice grubu, sistem hatası yok). Jar'ın içindeki üç okuyucudan ikisi (commons-compress `ZipFile`, `java.util.zip.ZipFile`) orijinal arşivi açıyor; yalnız ön-kontrolün akış okuyucusu düşüyor.
- Bizim tarafımızda karşılık gelen bir körlük yoktu ama **uyarı da yoktu**: arşivi sorunsuz okuyup çerçeve kusurunu sessizce geçiyorduk. Bu kural o boşluğu kapatır.

### GTFS spec referansı
- GTFS Schedule Reference dataset'i bir **ZIP arşivi** olarak tanımlar ama arşivin iç çerçevesine hüküm getirmez; bu yüzden kural `Spec` DEĞİLDİR.
- 🔗 https://gtfs.org/documentation/schedule/reference/#dataset-files
- İhlal edilen belge: PKZIP APPNOTE 4.4.4 (general purpose bit 3 set ise yerel başlıktaki `crc-32`/`compressed size`/`uncompressed size` alanları sıfır olmalı ve doğru değerler verinin ardındaki data descriptor kaydında bulunmalıdır).
